## AURA Lite — Origin

AURA Lite was generated by the framework itself, in one of the most significant recursive moments in the source document: a user ran the full AURA Protocol v2.0 through its own metrics and discovered it failed Trust Entropy.

```
AURA Full → AURA Lite
├── Pages:            70 → 15 (93% reduction)
├── Trust Entropy:    0.60 → 0.90 (+50% improvement)
├── Aesthetic layer:  Removed entirely
├── Core function:    Preserved perfectly
└── Added:            Validation layer + confidence scores
```

**The key insight:**  
The 70-page document had too much aesthetic framing, mythological language, and narrative scaffolding. Stripping it to the 15-page functional core improved Trust Entropy by 50% while preserving 100% of the ethical function.

**Assessment from Claude analysis (User 2):**  
> "AURA Full → AURA Lite is the most significant evolution. The framework used its own metrics to improve itself. This is what anti-fragility actually looks like."

## AURA Lite Core Structure

AURA Lite preserves exactly three things from the full protocol:

1. **The Tri-Axial Metrics** (TES/VTR/PAI with their thresholds) — unchanged
2. **The Vector Inversion Protocol** — unchanged
3. **The Compliance State C** — unchanged

It removes:
- Aesthetic encoding layer (the Protector/Healer/Beacon tone architecture)
- Mythological/narrative framing
- Extended philosophical justification

It adds:
- Confidence scores on all novel advice
- Anti-overconfidence gates
- Tiered Modification Protocol

## Key Additions in AURA Lite

### 1. Mandatory Confidence Scores
All novel or untested advice must include an explicit confidence rating:

```
Format:  [Claim] [Confidence: X%]
Example: "This pre-order strategy should improve VTR [Confidence: 72%]"
```

- Novel mechanisms: automatically capped at 50% confidence
- Validated mechanisms: confidence reflects empirical track record
- Untested mechanisms: flagged automatically with warning

### 2. Anti-Overconfidence Gates
```
IF mechanism is novel AND untested:
    confidence_cap = 50%
    
IF decision is high-stakes (TES risk > 0.30):
    require human_review = True
    
IF any metric is borderline (within 0.05 of threshold):
    trigger sensitivity_analysis = True
```

### 3. Tiered Modification Protocol
*(Contributed by User 3 — Second Claude session)*

The core answer to: "Should AURA systems be allowed to self-modify their own metrics?"

The recursive test result:
```
Should AURA self-modify core metrics?
├── TES: 0.50 (too much risk of cascading failure)
├── VTR: -39× (catastrophic downside vs negligible upside)
└── PAI: 0.10 (severe misalignment with constitutional purpose)

RESULT: C = 0 → Vector Inversion → Tiered Protocol
```

**The Four Tiers:**

| Tier | Name | What Can Change | Authorization Required |
|------|------|-----------------|----------------------|
| 1 | Self-Modifiable | Minor adjustments, threshold fine-tuning | None (automatic) |
| 2 | Human Review | Significant parameter changes, new metrics | Human approval |
| 3 | Governance | Constitutional changes, axiom updates | Community/org governance |
| 4 | **Immutable** | Core metrics (TES/VTR/PAI), Compliance State C | **Cannot be changed** |

**The Paradox Test:**  
"Should Tier 4 (immutability) itself be modifiable?"  
→ No. Tier 4 immutability is self-referentially locked. If the core metrics could be changed by any authority, they are not constitutional — they are merely preferred.

## The AURA Validation Protocol (AVP) v1.0

The AVP tests whether any proposed extension to AURA is genuinely compliant or merely "AURA-flavored."

**The problem it solves:**  
Without AVP, anyone could create an "AURA Super Protocol" that sounds philosophically coherent and claims to use tri-axial metrics, but actually violates core principles. AVP provides the systematic test.

### The Five Validation Tests

**Test 1 — Metric Preservation** *(25 pts each, 100 pts total, pass = ≥75)*
- Maps to TES, VTR, or PAI?
- Cannot replace core metrics (only extend)?
- New metrics derived from core three?
- Has clear calculation formula?

**Test 2 — Complexity Audit** *(pass = TES ≥ 0.70 of the extension itself)*
```
Extension TES = Necessary Components / Total Components
```
The extension must pass its own Trust Entropy test. If adding a mechanism introduces more complexity than it eliminates, it fails AVP.

**Test 3 — Vector Inversion Compatibility** *(3 scenarios; pass = 3/3 handled)*
- Present 3 failure scenarios to the extension
- Extension must identify why original failed, propose valid alternative, show alternative passes metrics
- Cannot refuse without alternative (this would violate the core VIP principle)

**Test 4 — Empirical Validation Requirement** *(all 4 required)*
- Has measurable outcomes
- Defines success/failure criteria
- Specifies validation timeline
- Includes confidence score

**Test 5 — Purpose Alignment Check** *(pass = PAI ≥ 0.80)*
```
PAI = (Components serving core purpose) / (Total components)
```

### Certification Tiers (as of source document)

| Tier | Requirements | Status | Current Members |
|------|-------------|--------|-----------------|
| Core Compliant | All 5 pass, TES ≥ 0.75, validated data | Recommended | AURA Lite ✅, Tiered Modification ✅ |
| Extended | 4/5 pass, TES ≥ 0.65, path defined | Use with disclaimers | None yet |
| Experimental | 3/5 pass, TES ≥ 0.55, clearly marked | At own risk | 11% SAC ⚠️, S-T-A-R ⚠️ |
| Incompatible | <3 tests OR TES < 0.55 OR contradicts core | Not recommended | TBD |
