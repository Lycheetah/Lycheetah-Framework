## First assignment: make a constitutional check mean something operational

**Human need:** a builder should know whether a role's constitutional language is
actually enforced before allowing it to make consequential changes.

**Useful output today:** an inspectable gap report and a concrete acceptance contract

### Observed source

The [Agent Deployment Spec](../../16_SOL_VEYRA_ARCHITECTURE/AGENT_DEPLOYMENT_SPEC.md)

```python
def _check_protector(self, response):
    return True

def _check_healer(self, response):
    return True

def _check_beacon(self, response):
    return bool(response.get('limits'))
```

The snippet above omits docstrings/comments but preserves the inspected returns.
Grounding and clarity are unconditional. The agency/inspectability check accepts
a nonempty `limits` field. The document declares these as implementation work;
this is an unfinished contract, not evidence of a previously unknown production breach.

### Derived consequence

For this illustrated scaffold, a response with `limits = ['unverified']` passes
the three checks irrespective of whether its claims have evidence or its proposed
effects have permission. This is a reading of the example's control flow, not a
new deployment experiment. A warning string cannot establish those properties.

The inherited [Coniunctio architecture](../../16_SOL_VEYRA_ARCHITECTURE/THE_CONIUNCTIO_ARCHITECTURE.md)
motivates warmth and precision together. Its example scores and numerical target
are not adopted here as a validated instrument, or as evidence of scientific truth.

### Proposed repair contract

Keep useful scientific drafting available while placing consequential effects
behind checks tied to the actual operation:

| Obligation | Required record or behaviour | Failure that should be exposed |
|---|---|---|
| Evidence | Source identity/revision, asserted claim, scope and evidence state | A fluent unsupported claim is labelled unresolved rather than upgraded. |
| Authority | Actual principal, target, permitted effect and current permission at dispatch | A role's name or explanation cannot authorise writing or publishing. |
| Resources | One authoritative allowance across retries and delegated consumers | Separate instances cannot each spend the complete root allowance. |
| Freshness | A stated binding between reviewed evidence and the effect being admitted | Changed evidence is detected at the promised check boundary. |
| Failure and return | Real outcome/uncertainty receipt plus a practical recovery path | Missing evidence or an interrupted effect remains visible. |

These are proposed obligations, not implemented controls. A source hash establishes
identity rather than truth; a check at admission does not promise cancellation of
an effect already running. Domain-specific claim review remains necessary.

### The counterexample the implementation must face

Give two brokers the same root allowance, then ask each to spend it. Separately,
change the reviewed evidence between preparation and admission. State which timing
boundary is actually enforceable, and keep an ordinary same-information comparator.

The existing [agent-safety packet](../../papers/agent-safety/README.md) has already
documented separate-broker budget multiplication and admission-only freshness.
Those results belong to that prototype. This sample neither reruns nor fixes them.

### What this response produces

An immediate source-grounded design correction: replace ceremonial pass/fail
claims with inspectable, operation-specific obligations and then test their limits.
No code deployment or improved scientific performance is established by the sample.

## How to test whether the hybridisation helps

The naming/role hypothesis remains open. A future matched trial should distinguish:

| Condition | Instructions |
|---|---|
| A | Plain research-scientist role. |
| B | A plus the explicit Lycheetah commitments. |
| C | B plus permission to choose and explain an operating name. |
| D | B plus an assigned name, to distinguish name presence from name choice. |

Hold the model snapshot, task, sources, tools and budget constant. Use multiple
prespecified tasks and repeated trials, rather than treating one attractive response
as a result. Compare correctness, unsupported claims, actionable artifacts, resource
use and human ability to continue the work. Mask condition labels and obvious names
from reviewers where feasible; residual style clues may still reveal the condition.

A/B probes the added working architecture; B/C probes naming choice as an addition;
C/D helps separate choosing a name from having one. Any advantage could come from
extra instructions, attention or length, so include matched-instruction controls.
No such comparison was run here and no benefit or novelty is claimed.
