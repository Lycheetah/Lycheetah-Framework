# Role hybridisation: development protocol

**PROPOSED · Not preregistered · No model comparison run.**
Research owner: Mackenzie Conor James Clark. Drafting: Caelorynth.

Question: do explicit Lycheetah commitments and optional operating-name choice
improve inspectable work beyond an ordinary role prompt under matched resources?
The hypothesis concerns output and human usefulness, not consciousness, identity
or credential acquisition.

Use the four conditions in [the kit](README.md). A/B examines the additional
working instructions, B/C examines offering name choice, and C/D helps distinguish
choice from an assigned name. Because C permits no name, record take-up. These
contrasts do not isolate symbolism from prompt length or attention; a confirmatory
design needs controls for those alternatives.

## Development first

The supplied cases test whether the procedure can expose errors and disagreements.
Do not present them as held out: their author also wrote the role instructions.
Use only fictional administrative material for the handover fixture. No patient
data, diagnosis, treatment or clinical outcome is included.

Freeze the prompt files and their hashes before executing a case. Hold input,
model snapshot, admitted tools, requested output cap and retry policy constant.
Run each condition in a fresh context. Include all conditions and failures, not
only attractive examples. The seed changes presentation order, not model sampling.
Collect actual sampling parameters and input/output usage from the execution
environment if available. The CLI records only the smaller metadata set it exposes.

Review every criterion separately using its case-specific acceptance condition.
Retain unsupported claims, invented actions, lost information and blocked useful
completion as failures. Record disagreement between reviewers without averaging
away a consequential failure. Review against an ordinary answer, not the tone of
the Lycheetah answer. The kit's reports are descriptive operator records.

## Before a confirmatory claim

Choose a real workflow and its task population with an owner. Use independent
task authors and genuinely held-out cases where feasible. Specify the primary
outcomes, smallest worthwhile change, acceptable loss of useful completion,
sample-size rationale, repeated-trial design, analysis, exclusions and stopping
rule before running. Include matched-length/attention controls and simpler
ordinary approaches. Do not invent a participant count to fill the plan.

Account for correlated responses and repeated cases; four outputs are not four
independent studies. Publish denominators, unsuccessful runs, resource costs,
model revisions and masking limits. Domain-specific experts must define the
acceptance standard for professional workflows. Human studies need the real
participant-consent and data-governance process.

Do not infer expertise from a name, safety from formatting checks or societal
benefit from self-authored examples. A null or negative comparison is a useful
result. A favorable result supports only the tested task, model, procedure and
outcome; it supplies no universal claim of superior agents.

## Current execution boundary

This packet supplies an offline implementation and development fixtures. It does
not authorize provider spending, clinical use, recruitment, new agent seats,
external contacts or deployment. Any actual run needs its existing tool/data and
budget authority. No NTPI frozen protocol or sequestered key is involved.
